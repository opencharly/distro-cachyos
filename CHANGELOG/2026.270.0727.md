## Summary

Adopt the deterministic `layer-charly` — the `layer-charly#10` tag `v2026.269.2324`
(which replaces the floating charly install with a version-pinned one) — across
this project, and bump the shared-closure `pod-charly-mcp` pin to the producer tag
that already pins the same `layer-charly` (`v2026.270.0631`).

**8 `layer-charly` pins** (verified by `git grep`, see "How tested"):
`box/githubrunner/charly.yml:16`, `box/openclaw-desktop/charly.yml:21`,
`candy/charly-marketplace/charly.yml:27`, and `charly.yml:79,107,502,1742,1834`
(`v2026.243.0408` → `v2026.269.2324`).

**2 `pod-charly-mcp` pins**:
`candy/charly-marketplace/charly.yml:35`, `box/charly-selftest/charly.yml:8`
(`v2026.243.0516` → `v2026.270.0631`).

**Why every `layer-charly` ref, not just the runner box.** The remote-layer
resolver unifies a repo's candy to ONE version project-wide and warns on any
multi-version reference. Bumping only `box/githubrunner` (the intended change)
makes `charly box validate` emit `layer-charly resolved to multiple versions`
(origin/main = 0 warnings), because the shared `charly-marketplace` closure still
pulled the old `layer-charly` through `pod-charly-mcp`. Clearing that at its
source required the producer bump first:

```
opencharly/pod-charly-mcp#6  (pin layer-charly v2026.269.2324)  -> v2026.270.0621
opencharly/pod-charly-mcp#7  (bring its candy gate current)     -> v2026.270.0631
  -> this PR
```

Because the resolver already resolves to the newest referenced version, this PR
does not change *which* layer-charly the other consumers effectively use — it makes
every declaration match that single resolution.
