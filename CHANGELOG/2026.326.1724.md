### R10, answered on the facts: there is no behaviour to discriminate

The round asked for a check that FAILS on `nvidia-cdi`. There cannot be one, because `nvidia-cdi` is
not a driver-baking base — it is this same base with two explicit pins. Its whole body at `main`:

```
$ git show origin/main:box/nvidia-cdi/charly.yml
    base: podcdi.pod-cdi
    candy:
        - '@github.com/opencharly/layer-agent-forwarding:v2026.274.0608'
        - '@github.com/opencharly/layer-cdi:v2026.323.1618'
        - '@github.com/opencharly/layer-cuda:v2026.323.1604'
```

So both bases compose `podcdi.pod-cdi` and the POD contract, and every bed (GPU-visible, inference,
`driver_files=0`) passes on either — the swap is a **deduplication plus a pin advance**, not a
contract change. What actually moves is those two pins: the import now carries
`pod-cdi v2026.326.0853` → `layer-cdi v2026.326.0828` → `layer-cuda v2026.326.0028`, and the pod-cdi
PR proved that chain on its built artifact (0 driver files, `libcudart` linkable, no `nvidia-ctk`).
A check able to fail on the OLD pins would have to assert the new release's behaviour specifically;
that is the producer's own fixture (`layer-cuda`'s `tests/strip-runtime-survives.sh`) and the
producer's guard (`nvidia-keeps-distro-driver`), both shipped in their repos.

The `layer-agent-forwarding` line is not an assertion either — it is the SAME tag `pod-cdi` composes:

```
$ grep -n 'layer-agent-forwarding' pod-cdi/charly.yml
88:            - '@github.com/opencharly/layer-agent-forwarding:v2026.274.0608'
```

so dropping the duplicate from the six boxes removes a second composition of the identical candy, and
`podcdi.pod-cdi` still supplies it.
