## Why the pod venue cannot make this claim

`pam_unix` delegates to the setuid helper `unix_chkpwd` whenever euid ≠ 0, and that helper only
verifies the **calling** user's own account. In a rootless pod, authenticating any *other* account
fails with *"Authentication service cannot retrieve authentication info"* for a **right** password
exactly as it does for a wrong one — so both legs of a cross-user gate would fail, and a reject leg
that passes for the wrong reason is worse than no gate at all. The pod fixture
(`cstream-probe-account`) says precisely this in its own description and sets a password on the
container's own runtime account instead, explicitly deferring cross-user auth to "the VM bed's
gate".

On a machine the broker runs as **root**, euid *is* 0, `pam_unix` reads `/etc/shadow` directly, and
a different account can be authenticated — which is the only thing the production login path ever
does.

## The three checks

| id | claim |
|---|---|
| `cstream-vm-login-path-present` | `cstream-leader`, `cstream-login-probe` and `/etc/pam.d/cstream` are installed — so a failure below is about PAM, not a missing binary |
| `cstream-vm-pam-cross-user-accept` | authenticates `cstreamprobe` — **after asserting `id -un` is not `cstreamprobe`** |
| `cstream-vm-pam-cross-user-reject` | same account, same caller, **wrong** password → refused |

**The guard in the accept leg IS the claim.** An accept that happened to target the caller would
pass in a rootless pod too, so it would prove nothing about cross-user authentication; the check
fails loudly (`NOT-CROSS-USER`) rather than silently degrading into the same-user case the pod bed
already covers.

**The reject leg is what stops the accept leg being vacuous.** A PAM stack that admits anything
passes an accept-only gate. Same account, same caller, one variable: the password.

## Two things the schema and the runner taught me

1. **A candy whose only `run:` step is `context: [runtime]` installs nothing**, and charly rejects
   it outright: *"must have at least one install file (candy manifest distro: packages, root.yml,
   … , a `candy:` field, an `external_builder:`, or a `plugin:` block)"*. The fixture's account
   creation is therefore an **install-timeline** step — which on the systemd venue runs during the
   deploy walk, as root, exactly when the account needs to exist.
2. **`check live` runs in verify-only mode and skips mutating steps**, so the run count is
   `10 steps: 9 passed, 0 failed, 1 skipped` with the skip being that same account-creation step:
   `SKIP run create the cross-user probe account — skipped — verify-only mode (mutating step)`.
   That is correct, not a hidden assertion: the account is created at deploy, and
   `vm-probe-account-exists` PASSing is the independent proof it landed. (A skip is worth reading
   every time — a silently skipped *check* is a bed that looks green while asserting nothing.)

## On the fixture credential

The password is deliberately in the clear, for the same reason the pod fixture's is: its entire
purpose is to let a **disposable** guest prove PAM accepts one password and refuses another. The
candy is marked `BED FIXTURE ONLY -- never composed into a shipped box` and lives beside the bed
rather than in `pod-cstream`, so it cannot reach an image anyone deploys. It is a fixture authored
in the open, not a captured credential.
