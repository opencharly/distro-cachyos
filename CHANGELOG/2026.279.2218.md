### Scope boundary (deliberate) — the dsh web GUI

The dsh **web** GUI is **not** composed here. `pod-dsh`'s `dsh-web` candy is a container
service (supervisord+socat on container port 3081 with a container `volume:`), which does not
suit a host workstation: on a `target: local` deploy it would render a *system* systemd unit
that cannot reach the deploying user's `~/.dsh` / `~/.npm-global`. On a host the web UI belongs
to a **user-scope** systemd unit, exposed **1:1** with
`tailscale serve --bg --https=3080 http://127.0.0.1:3080` (the `tailscale-up` candy already
arms the operator permission; port 443 is left free). A reverse-proxied deployment must start
`dsh web --trusted-host <host>:3080` (the Host/Origin fence). That is an operator step,
documented by `/charly-tools:dsh`; baking a host/port-specific unit is out of this profile's scope.

## How tested

### The disposable VM witness (R10) — what it proves, precisely (R3)

`charly check run check-dsh-cachyos-vm` boots a fresh CachyOS VM, `add_candy`s the SAME two
`pod-dsh` refs the profile adds, installs them on the guest over SSH, and runs the SAME five
probe **commands**. It does **not** execute the profile's own `charly.yml` plan: the profile's
probes are `command: {command: …, in_container: false}` (they must run on the operator's real
host), whereas a bed probe uses the `command: <scalar>` form routing to `cc.Exec()` (the guest's
SSHExecutor). The shell **bodies are byte-identical**; only the execution venue differs, and it
must, because a `target: local` host-side probe cannot run against a guest. So the bed proves
**the two refs install and behave on CachyOS** (a broken ref, or a candy that fails to install,
fails the bed) — not the profile's literal plan. The profile's own five probes remain to be
run by the operator's `charly update charly-cachyos` on the real workstation.
