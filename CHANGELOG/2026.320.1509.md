## Summary

Adds `cachyos-coder-tools` and its R10 bed `check-cachyos-coder-tools-pod` — the **compensating
gate** for the layer candies the retired non-CachyOS coder workstations were the only live proof of
(opencharly/opencharly#1068).

The retirement landed in `distro-arch` (`9da5521`) and `distro-debian` (`835e409`), and is in flight
in `distro-ubuntu`. Those three coder beds were the ONLY gate for six layer candies — measured: no
other bed in the org composes them, and each of their own repos declares no `pod:`/`vm:` entity.

This image composes **four** of the six on the CachyOS base — `pixi`, `language-runtimes`, `typst`,
`github-actions` — plus `pod-sshd` so the pod has a long-running service, and nothing else.

**The other two cannot be compensated anywhere, and both are filed defects in the candy that owns
them** (see `## Filed issues`):

- `google-cloud-npm` — its required `layer-google-cloud` cannot complete `install.sh` inside a
  buildkit build container, while the identical installer succeeds `rc=0` in a plain container of the
  same base.
- `grafana-tools` — its plan needs `unzip`, the candy declares no `distro:` section at all, and no org
  candy provides unzip for `pac`.

`rpmfusion` is **not one of the six** — it is a SEPARATE candy that the retired `fedora-coder` was
also the only gate for, and it cannot move to CachyOS at all: RPM Fusion is driven by
`dnf`/`rpmkeys`/`rpm -E %fedora` with no Arch analogue. It keeps its own minimal Fedora bed
(`distro-fedora`'s `fedora-rpmfusion`). So the count is six candies in this image's scope (four
composed, two filed), plus `rpmfusion` handled in its own repo — never "the sixth".

**Why minimal, not a workstation.** The first draft composed `fedora-coder`'s entire 26-candy stack
and could not build: the composed `ai.opencharly.description` label reached **121,320 bytes on one
generated Containerfile line**, over buildkit's hard 65,535-byte per-line limit. Re-scoped to what
the compensation needs, the largest label line measures **63,764 bytes**.

**Why earlier attempts failed, and the corrected root cause.** My first reading blamed ADE agent
grading. That was wrong, and a control refuted it: `distro-fedora`'s `check-fedora-rpmfusion-pod`
carries the same `pod-sshd` agent-check, reports the same skip, and **passes**
(`PASS (steps=16, skipped_checks=12)`). The skip is therefore not a failure mode — the passing run
above reports `skipped_checks=16` and is still green.

The real mechanism is **disk exhaustion**, and it is in the runner's own stderr:

```
$ grep -iE 'no space|ENOSPC' .check/check-cachyos-coder-tools-pod/2026.320.1427/runner.stderr.log
charly check run …: writing .check/…/image-build.log: … no space left on device
charly check run …: writing .check/…/summary.yml:     … no space left on device
```

The bed writes each step's log and then `summary.yml` under `.check/<bed>/<calver>/` on the host
filesystem — which a bed build is simultaneously filling with layers and buildkit cache. When that
write fails, the step is graded from whatever could be recorded, so the failure surfaces as
`[image-build] FAIL` and (in the other run) as `charly subcommand exited -1` with a one-line log.
**Two runs, two different opaque verdicts, one capacity cause** — and the host was at 92 % of a 400 GB
filesystem.

That diagnosis is filed so it is not lost: **opencharly/charly#1170** — a bed's log/summary write
failing for lack of space is reported as an opaque subcommand exit rather than a named capacity
diagnostic. With the disk freed, the same bed on the same tree went **fully green** (run
`2026.320.1440` above), which is the evidence that capacity — not code — was the cause.
