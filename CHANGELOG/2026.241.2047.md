# 2026.241.2047 — feat: punktfunk streaming-host image and its two disposable beds

## Summary

Completes punktfunk support in charly with the deployable image and the beds that prove
it. `layer-punktfunk` (the host install) and `plugin-punktfunk` (the `punktfunk:` check
verb) already landed; this is where they are composed and gated.

**`box/punktfunk-host`** — cachyos base + `pod-sway` (headless wlroots) + the punktfunk
candy + the punktfunk verb plugin. The compositor is not scenery: punktfunk creates its
virtual display by calling `swaymsg create_output`, so without sway's IPC socket the host
runs but can never produce a display. GPU-free by construction — the candy's `host.env`
pins `PUNKTFUNK_ENCODER=software` and `PUNKTFUNK_ZEROCOPY=0`, so the image runs anywhere.

**Two beds, one per venue, because one bed cannot prove both halves of the candy:**

| bed | venue | what only it can prove |
|---|---|---|
| `check-punktfunk-pod` | container (supervisord) | supervisord cannot use a systemd user unit, so the host is launched by the candy's **wrapper**, which waits for sway's IPC socket. Also the only place the `punktfunk:` verb's **live dispatch** runs, including discovering the host-generated bearer token inside the venue. |
| `check-punktfunk-vm` | real systemd guest | the **PACKAGED** `punktfunk-host` user unit, **lingering**, and the management plane under a real init — none of which a container venue can demonstrate. |

The VM bed boots an **Arch cloud image** rather than the cachyos pacstrap bootstrap: what
is under test is the systemd user-unit path, and a prebuilt qcow2 reaches a booted systemd
guest in a fraction of the time without changing that. punktfunk's pacman repo is the same
on Arch and CachyOS. `firmware: bios` follows `/charly-vm:arch-cloud-vm` Finding B (the
EFI path boots a stale embedded grub.cfg and loses the console to the simpledrm takeover
race). `curl` is in `cloud_init.package` for a load-bearing reason: the `punktfunk:` verb
issues its management-API requests from **inside** the venue, because punktfunk binds that
API to loopback by design.

### The VM bed asserts its own claims, and here is why

The first VM run of this bed passed with only **2 steps** — its own plan — because when the
punktfunk candy arrives as an `@github` `add_candy:` ref, its baked checks are **not**
collected into the bed's `check-live` run. (With the same candy resolved locally during
development, they were: 15 steps.) A bed that passes without asserting what its description
claims is worse than no bed, so the three load-bearing assertions — packages, the packaged
user unit, the live management API — are stated in the bed's own plan, and the run above is
the result.

I have **not** filed that as a defect: I have not isolated the variable cleanly
(local-vs-remote candy resolution is one difference between the two runs, and I did not rule
out others), so asserting a charly bug from it would be a guess. It is recorded here as a
measurement, and the bed is correct either way.
