# 2026.241.1436 — fix: repoint the candy refs at the extracted standalone repos

## Summary of changes

The candy de-submodule cutover moved these candies out of `charly/candy/` into their own
kind-prefixed repos. This repo still pinned them by a path **inside charly**
(`@github.com/opencharly/charly/candy/<name>:<charly tag>`).

**7 refs**, all in `candy/charly-marketplace/charly.yml`, now point at the standalone repo at its
own current tag. A second file (`charly.yml`) changes only its header comment — no ref rewrite
lives there. An earlier revision of this body said "7 refs across 2 files", which overstated the
spread; corrected.

| was `charly/candy/…` | now |
|---|---|
| `charly-build` | `layer-charly-build` |
| `charly-check` | `layer-charly-check` |
| `charly-image` | `layer-charly-image` |
| `charly-immich` | `layer-charly-immich` |
| `charly-internals` | `layer-charly-internals` |
| `charly-internals-extra` | `layer-charly-internals-extra` |
| `charly-kubernetes` | `layer-charly-kubernetes` |

### Why this is not cosmetic

These refs are **not broken today** — they name *old* charly tags that still contain the
directories. That is precisely the failure this cutover exists to remove: **content frozen at a
stale pin, with every gate staying green.** charly's `main` no longer has those directories at all
(`opencharly/charly#451`), so the next pin bump would turn a silent staleness into a hard break.

### Two refs are deliberately left alone

`charly` and `charly-mcp` still resolve through `charly/candy/…` — **9 refs** across 5 files (7 for
`charly`, 2 for `charly-mcp`). An earlier revision of this body called this "the 2 deliberately-held
refs", conflating candy NAMES with ref COUNT; corrected. Repointing them here makes this
repo **fail validation**:

```
charly: error: command "validate": 8 validation errors:
  remote candy name conflict: "charly" provided by both
    github.com/opencharly/layer-charly and github.com/opencharly/charly
  remote candy name conflict: "charly-mcp" provided by both
    github.com/opencharly/pod-charly-mcp and github.com/opencharly/charly
  …
```

Something else in this repo's closure still provides those two from the charly repo itself, so
after a repoint both a standalone repo *and* charly supply the same name. Before the repoint both
sides resolved to the same provider, which is why the conflict was invisible. That is the
pre-existing defect tracked as **`opencharly/charly#437`** — *"charly box validate: 18 'remote candy
name conflict' errors — plugin candies referenced by check-bed verbs appear as provided by both
charly and the standalone repos"* — and this PR routes them there rather than shipping a repo that
does not validate.

Their pins are left **byte-identical**, at their original and deliberately differing tags
(`v2026.240.0831` and `v2026.240.2219`), so nothing is silently re-pinned while being held back.
