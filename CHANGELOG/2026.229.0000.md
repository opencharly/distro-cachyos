# 2026.229.0000 — the 2026.229.1634 landing-order graph was wrong twice

A correction to a landed entry, recorded here as its own dated event because this release takes a
tag and every tag in this repo maps to a `CHANGELOG/` file.

## What was wrong

`CHANGELOG/2026.229.1634.md` described the cutover's landing order as a five-link serial chain:

```
distro-arch → distro-cachyos → spec → sdk → superproject
```

**The `distro-cachyos → spec` edge does not exist.** Measured on each repo's `main`, not inferred:
`spec` has zero code references to any `opencharly/distro-*` repo and no such `go.mod` require;
`sdk` likewise, its one mention being a comment in `deploykit/graph_shim_relocated_test.go`. Neither
was ever gated by this repo's tag. `spec → sdk` IS real (a `go.mod` require); the chain's other half
is not.

## What the first fix got wrong

The first attempt replaced that false edge with **another false edge** — `distro-fedora →
distro-cachyos` — and, to do it, deleted the sentence *"with `distro-fedora` parallel to the first"*,
which had been correct.

This repo imports exactly one distro repo: `charly.yml:39 → distro-arch:v2026.229.1615`.
`distro-arch` imports none, so there is no transitive path. The superproject imports all five distro
repos flat and independently (`charly.yml:25-29`), which makes `distro-fedora`, `distro-debian` and
`distro-ubuntu` **siblings** of this repo, not inputs to it.

## The corrected graph

```
distro-arch  →  distro-cachyos  ──┐
distro-fedora ────────────────────┤
distro-debian ────────────────────┼─→  superproject
distro-ubuntu ────────────────────┤
spec  →  sdk  (no distro pins) ───┘
```

## Why both errors survived their own review

The original claim looked right because the tags landed in ascending time order. But a chain
*entails* ascending order; ascending order does not entail a chain — reading one off the other is
affirming the consequent. Only the dependency grep discriminates.

The second error survived because **the greps were pointed at the claim being retracted, never at the
claim being asserted.** The `spec`/`sdk` half was measured; the fedora edge arrived as scenery in a
diagram and was never checked. A correction is a new claim and earns no exemption from the test that
caught the old one — verify the replacement, not just the retraction.

Both retractions are left visible in the 2026.229.1634 entry rather than silently patched: a reader
who lands there to learn why that tag exists meets the corrected graph, and the record of how it was
got wrong is the part worth keeping.
