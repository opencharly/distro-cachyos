# 2026.243.1942 — feat(WP5): gate that the desktop locks itself once the last viewer leaves

## Summary

Gates WP5: the desktop must lock itself once the last viewer has been gone long enough. Three
checks, and **the order is load-bearing**:

| # | check | asserts |
|---|---|---|
| 1 | `cstream-lock-idle-only` | nothing is locked while nobody has ever watched |
| 2 | `cstream-frame-through-webrtc` | a real consumer connects and leaves — *moved here* |
| 3 | `cstream-lock-after-detach` | `hyprlock` appears within the bound |

**The diff changes no pins.** `git diff origin/main -- charly.yml | grep '@github.com'` is empty
and `box/` is byte-identical to main, which already carries
`layer-cstream-desktop:v2026.243.1831` — the tag that puts `CSTREAM_LOCK_AFTER` in the image. One
file, checks only.

## Why the frame check moved

`hyprlock` takes an `ext-session-lock`. A lock client that is **killed rather than
authenticated** leaves the compositor locked with no client — the session cannot be recovered from
outside, only re-locked. So wherever the lock fires, every check after it reads a lock screen
instead of the desktop.

`cstream-frame-through-webrtc` is the only check in this bed that connects a WebRTC consumer, and
its departure starts the countdown (`CSTREAM_LOCK_AFTER=10`). Left where it was — before the
clipboard and screenshot checks — the lock would have landed in the middle of them, and
`wl-screenshot-content` would have kept **passing** while silently asserting something else: that
the *lock screen* has non-uniform content. A check that quietly changes what it proves is the
exact failure this bed exists to catch, so the reorder is not cosmetic.

Nothing may be appended after these three; the bed says so in a comment at the head of the block.

## Why check 1 exists

Without it the pair passes for free against an arming bug that locked at **startup**. From
outside, "locked because a viewer left" and "locked since boot" are the same `pgrep`. Check 1 also
fails loudly if a future edit puts a consumer-connecting check earlier — which would otherwise
present as a mysterious `wl:` failure ten checks later, naming the wrong layer.

The wait in check 3 is charly's own `eventually` / `retry_interval`, not a hand-rolled poll loop:
it stops the moment the lock appears, and fails if it never does.

**The attempt count is what makes check 3 more than a `pgrep`.** With `CSTREAM_LOCK_AFTER=10` and
a 5s retry interval, the early attempts find nothing and a later one finds `hyprlock` — so the
lock fired *because of* the departure and no earlier than the configured delay. A lock that was
already running would have passed on attempt 1, and check 1 passing beforehand rules that out from
the other side. Reproduced across both legs.
