### RCA — the missed control (this round)

Two findings reached this PR because my own pre-push gate could not see them, and both are named here
rather than summarised away:

1. **The build-drive defect** (`#3 [internal] load metadata for ghcr.io/opencharly/arch-builder:<tag>:
   not found`). My gate was the bed run and it DID fail — but I then ran it with a locally patched
   binary (a temporary `replace` of plugin-build) and reported that PASS as the gate. **The missed
   control: a gate must run on the module graph the repo actually ships; a locally patched dependency
   proves the patch, not the tree.** It was caught by the validator as "a green run on an unshipped
   patched binary". Root fix landed downstream — plugin-build#54 → charly#1139 — and every run pasted
   here since states its provenance (`charly/go.mod` requiring `plugin-build v0.2026317.2215`, binary
   `2026.317.2237` built from post-merge main).

2. **The packaging warning.** For a whole round I believed this gate was clean, because `box validate`
   printed the `krun-host` warning and then summarised `0 warnings` in the SAME run. **The missed
   control: trusting a summary count instead of the thing it summarises.** That count defect is real
   and filed (`plugin-box#80`, closed unmerged); the durable fix on my side is to measure what the
   summary claims — every warning claim in this body is a raw `grep -c "Warning:"` on the output,
   which no counting bug can falsify.

3. **The warning's cause was then fixed at its owner, not argued away.** `layer-containerd` carried one
   packaged-only service (`buildkit`) beside its dual-venue `containerd`; `opencharly/layer-containerd#10`
   split the builder into its own host-oriented candy (`DESIGN.md` D-CANDY-3 forbids a candy naming an
   init system, so the concern moved rather than the lint), and `opencharly/distro-cachyos#165` advanced
   `krun-host`'s ref. On that main `box validate` prints **0** `Warning:` lines where it printed one.

**Rollout note, not evidence.** The operator separately directed an in-place upgrade of the live,
non-disposable deployment; it ran with a verified `/opt/data` snapshot and now serves 0.13.3 on the
same published port. DISP governs autonomous destroy/rebuild, which that was not.

## Change classification

The `openwebui` image built from this box serves open-webui 0.13.3 instead of 0.12.3, and the bed
asserts it. **Breaking change + rollback:** consumers get a new Open WebUI minor with six additive
Alembic migrations on first boot; rolling the IMAGE back alone bricks startup
(`CommandError: Can't locate revision`), so the rollback is the `/opt/data` snapshot restored together
with the image.
