## Bump the `distro-arch` import pin to `v2026.229.1615`

`import:` pinned `@github.com/opencharly/distro-arch:v2026.200.2132`. That published copy declares a
`cloud_image` VM source with no `source.distro`. The vm kind's `OpValidate` rejects that — but note
the tense: **that check is not on `main` yet.** It lives on the unmerged superproject branch of this
cutover, and `spec@origin/main` still types the field optional and open. So the reject reproduces
only against a binary built from that branch, which is what the mutation below used. The bump is
correct and safe today regardless: the new tag is a strict improvement on the old one, and nothing
about it depends on the check landing. Once it does land, every project-loading command that reaches
this repo through the import chain would fail on the old pin, not just a VM build. `v2026.229.1615` is the first `distro-arch` tag carrying the field (verified by cloning the
tag and parsing it: `entity=arch distro='arch'`), so the pin moves to it.

**This repo is a transitive link, and that is why the bump has to land here rather than upstream.**
The superproject imports the PUBLISHED `distro-cachyos` tag, not a local checkout, so the chain is:

```
charly (superproject)  →  distro-cachyos@<tag>  →  distro-arch@<tag>
```

Editing this file in a local `box/cachyos` submodule changes nothing for the superproject until this
repo is re-tagged. Measured: after bumping the superproject's own `arch` pin, its suite still
resolved `distro-arch@v2026.200.2132` — sourced from the cached published `distro-cachyos@v2026.204.1336`,
not from the local edit. One of four failing tests cleared; the rest need this tag.

So the landing order has five links, not four: `distro-arch` → **`distro-cachyos`** → `spec` → `sdk`
→ superproject, with `distro-fedora` parallel to the first.
