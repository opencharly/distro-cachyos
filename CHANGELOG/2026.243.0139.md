# 2026.243.0139 — feat(WP5): gate the Hyprland half of the dual-sided keymap

## Summary

Gates the **Hyprland half** of WP5's dual-sided keymap: switching `input.kb_layout` at runtime and
proving the compositor actually applied it.

**One changed file:** `charly.yml` — 3 checks added to `check-cstream-pod`. No new candy, no pins,
no Go.

| id | action | observation |
|---|---|---|
| `hypr-keymap-baseline` | — | the keyboard is **not already** on `de` |
| `hypr-keymap-set` | `wl: hypr-eval` running `hl.config({ input = { kb_layout = "de" } })` | — |
| `hypr-keymap-observed` | — | the compositor's own device report says `"layout": "de"` |

## Why the baseline check exists

Without it the observation is vacuous: asserting `de` after the switch proves nothing if the
keyboard was already `de`. The baseline fails loudly (`KEYMAP-BASELINE-ALREADY-DE`) rather than
letting the pair degrade into a tautology.

## Why `hypr-eval` and not `hypr-keyword`

**`hyprctl keyword` is a no-op that reports success on Hyprland 0.56.2.** `plugin-wl` removed the
`hypr-keyword` method for exactly this, and records the measurement at its own resolution call site:

> keyword answers "keyword can't work with non-legacy parsers. Use eval." **AND EXITS 0** — the
> resize would report success and change nothing. Measured on 0.56.2; the same defect that removed
> the `hypr-keyword` method.

The method is gone from `#WlInput.method` accordingly, so `hypr-eval` with a Lua expression is the
only route — which is also what the plan specifies for the Hyprland side.

## Why the observation is a device report, not the verb's exit code

**`hyprctl eval` answers `ok` for any expression** — valid, invalid, or a no-op. The verb's success
therefore says nothing about whether the config changed. Only `hyprctl -j devices` reporting the new
layout does, and the failure branch prints the keyboards block so a mismatch is diagnosable from the
bed output.

## The GWD half is deliberately NOT re-checked here

`layer-gst-wayland-display` already owns it — `gwd-keymap-properties`, running `gst-inspect-1.0
waylanddisplaysrc` and asserting `xkb-layout` / `xkb-variant` / `xkb-options`, none of which exist
in stock gst-wayland-display. That layer **builds** the plugin, so it is what can tell a patched
fork from upstream; a bed re-checking it asserts someone else's invariant somewhere it cannot fail
differently.

**I wrote a duplicate of it and removed it in this branch**, and it is worth recording how it was
caught: `charly box validate` passed, and *both* copies passed, so the only symptom was
`check-live` printing the same id twice. A duplicated check does not fail, does not warn, and is
invisible to every gate except reading the output. A comment now records where the other half lives.

## What this does NOT claim

**Character-level mapping is not gated, and deliberately so.** `wl: type` drives `wtype`, which
sends *keysyms*, not scancodes — so typing "z" produces "z" under any layout, and a character-based
assertion would pass identically with the keymap unset. Gating it would be asserting a property the
available input tooling structurally cannot exercise. What is gated is that the compositor accepted
and reports the layout; proving character mapping needs a scancode-level injector this stack does
not have.

WP5's remaining item — lock/idle (`hyprlock`) — is untouched and still open.
