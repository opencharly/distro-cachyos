## What the bed gates

| id | claim |
|---|---|
| `cstream-vm-systemd` | systemd is the running init, so the unit path is the one under test |
| `cstream-vm-units-rendered` | the daemons are `charly-<candy>-<service>.service` units, not `[program:]` entries |
| `cstream-vm-session-target-installed` | the session target **loads** (`LoadState`, not file-exists) and is not enabled at boot |
| `cstream-vm-compositor-session-scoped` | the compositor unit is rendered, is **not** in `multi-user.target.wants`, and its `[Install]` names the session target |
| `cstream-vm-streamer-installed` | the streamer binary landed on this venue too |

Three of these encode traps that each cost a bed cycle:

- **charly names a rendered unit `charly-<candy>-<service>.service`**, not the bare service name.
  The first version of `cstream-vm-units-rendered` asserted `cstream-parent.service` and failed
  against a *correctly* rendered unit.
- **`test -f` on a `.target` proves nothing.** A unit with a syntax error still exists on disk while
  systemd refuses to load it, and a `WantedBy` pointing at it silently resolves to nothing.
  `systemctl show -p LoadState` forces the load — and it is what caught a `pod-cstream` step that
  installed **nothing** while `deploy-add` exited 0.
- **A failing check must name its own cause.** charly surfaces **stderr** on a failed step; these
  checks originally echoed to stdout and produced a bare `exit=1, want 0 (stderr: )`, collapsing
  three distinguishable causes into one opaque code. Every failure branch now writes to `>&2`.

## One mkinitcpio cause fixed at source — and a correction to my own earlier claim

The guest's initcpio hook escalated warnings into `==> WARNING: errors were encountered during the
build` → `error: command failed to execute correctly`, tripping charly's log-diagnostic gate on
**every package install that fired the hook**, including the deploy.

**`btrfs-progs` is the fix** — it supplies `fsck.btrfs` for the btrfs rootfs, so `No fsck helpers
found` disappears and the hook stops escalating. Measured in `deploy-add` across retained runs
(`1801`–`1921` vs `1934`+):

| line | before | after |
|---|---|---|
| `error: command failed to execute correctly` | 1 | **0** |
| `errors were encountered` | 1 | **0** |
| `No fsck helpers found` | 1 | **0** |

Allowlisted build lines drop **6 → 4** (`1921` → `1934`).

**Correction:** an earlier commit message in this branch said *"two mkinitcpio warnings are fixed at
source"*. Only one is. The second half — writing `/etc/vconsole.conf` from `cloud_init.runcmd` —
never ran at all, which is the next finding.

## The `cloud_init:` block was inert, and is deleted rather than left looking load-bearing

Measured on the live guest:

```
cloud-init status --long   ->  status: error
                               "No instance datasource found."
/var/lib/cloud/instance/scripts/runcmd  ->  No such file or directory
virsh dumpxml                           ->  no <disk device='cdrom'> at all
```

charly **builds** `output/qcow2/cstream-vm/seed.iso` (same mtime as `disk.qcow2`) and never attaches
it: seeding lives in `plugin-vm/vm_cloud_image.go`, i.e. it is a `kind: cloud_image` feature, and
this entity is `kind: bootstrap`. A pacstrapped guest is configured in the **chroot** instead —
charly's arch bootstrap already runs `arch-chroot systemctl enable sshd qemu-guest-agent
cloud-init-*`. That is the only reason ssh works here, and it is exactly what made an inert
`runcmd` list look like it worked.

Ruled out as the cause: this entity's own `libvirt:` block. Removing it and re-creating the domain
still yields **zero** cdrom devices.

### Every surviving warning, enumerated and root-caused (R10 / R1)

The container venue is at **zero**. The systemd venue's 16 are pacstrap-inherent, pre-date this
change, and are listed in full:

| warning | count | root cause | why acting on it would be a workaround |
|---|---|---|---|
| `==> WARNING: sd-vconsole: "/etc/vconsole.conf" not found` | 3 | mkinitcpio's `sd-vconsole` hook runs inside the **pacstrap chroot**, before any first-boot configuration exists. | Unreachable from the entity — `cloud_init` is inert on this source kind and would run long after the chroot regardless. Allowlisted by charly's `mkinitcpio-chroot-warnings` rule; harmless since `btrfs-progs` stopped it escalating. |
| `warning: <pkg>: local (N) is newer than cachyos-v3 (N)` — `zstd`, `libtool`, `binutils` | 2 each | The pacstrap base is built from a newer snapshot than the `cachyos-v3` repo the guest syncs against; pacman advises rather than downgrades. | Inherent to a rolling distro; pinning older packages to silence it is exactly the workaround R4 forbids. |
| `warning: <pkg> is up to date -- skipping` — `shadow`, `rust`, `pam`, `libcap`, `base-devel` | 2 each | The candy's `package:` list names packages the pacstrap base already provides. | Load-bearing on the **other** venue: the container base does not provide them. | `warning: /etc/pacman.conf installed as /etc/pacman.conf.pacnew` | 2 | A package update ships a new `pacman.conf`; pacman writes `.pacnew` rather than overwrite. | Expected pacman behaviour on any guest whose `pacman.conf` has been touched. |

## Environment constraints found while building this bed

Worth recording — each cost a run, and none is discoverable from the schema:

- charly builds the guest disk in **two** places: `<project>/output/qcow2/` (so the *project* must
  not sit on a small tmpfs) **and** `$TMPDIR/charly-priv-N`, which needs **~42 GiB** for a 40G
  guest. Both default to `/tmp`.
- **`accel3d: true` requires a GL-capable display backend.** Without
  `graphics: [{type: egl-headless}]` qemu refuses to start — *"The display backend does not have
  OpenGL support enabled"* — a ~7 s `vm-create` failure, well before boot. `accel3d` is
  load-bearing here: `gst-wayland-display` creates the `zwp_linux_dmabuf_v1` global only on a
  hardware render target, and Aquamarine's Wayland backend hard-requires it.
