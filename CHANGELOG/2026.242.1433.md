# 2026.242.1433 — fix(cstream): advance to the metalayer whose transport can carry media

## Summary

Advance both cstream boxes to `layer-cstream-desktop v2026.242.1424` — the first metalayer whose
WebRTC transport can actually carry media.

**What it fixes.** The stack negotiated a WebRTC session end to end — producer registered, consumer
registered, `startSession` sent, `started a session` logged — and then carried **no media**, with no
ICE or DTLS error anywhere. Root cause, read off the producer's own log rather than inferred:

```
SessionPipelineError { session_id: "…", peer_id: "…",
                       details: "Failed to make element webrtcbin" }
```

`webrtcsink`/`webrtcsrc` come from `gst-plugin-rswebrtc` and were present, but they construct a
**`webrtcbin` per session internally**, and that element ships in `gst-plugins-bad` — never
installed, only `gst-plugins-bad-libs` (the shared libraries, pulled in transitively). So
`/usr/lib/gstreamer-1.0/libgstwebrtc.so` was absent and `gst-inspect-1.0 webrtcbin` exited 1.

The construction failure is a **WARN, not an error**, so nothing surfaced: the sink registered, the
session started, the offer was never sent, and every consumer waited until timeout. **That is why
earlier work on this stack found "no ICE/DTLS error" — there was no `webrtcbin` to perform ICE or
DTLS at all.**

Measured on one pod with the package as the only variable:

```
BEFORE  webrtcbin ABSENT   frames received 0      "Failed to make element webrtcbin" x1
AFTER   webrtcbin PRESENT  frames received 1683   (55,988,362 bytes)                 x0
```

**The advance also brings a new gate.** `cstream-webrtcbin-registered` asserts the element itself.
Its neighbour `cstream-webrtcsink-registered` **passed throughout the entire outage** — it checks
that the sink registers, which says nothing about whether it can serve a session. Registration is
not capability, the same trap `cstream-streamer-graph` already covers by asserting the VA encoder
*opens*.

### 3. A finding ruled out, recorded so it is not re-chased

A competing hypothesis was measured and **refuted**: the pod has no global IPv6 (only `::1` and
link-local), while `webrtcsink`'s default `stun-server` is `stun://stun.l.google.com:19302`, which
resolves IPv6-first inside the container to an address that is `Network is unreachable` — with a
working IPv4 record beside it. It predicted the symptom exactly and was still wrong: `webrtcbin` was
never created, so ICE never ran and the STUN server was never contacted. It stays a latent issue for
when ICE *does* run, and this PR does not claim it.
