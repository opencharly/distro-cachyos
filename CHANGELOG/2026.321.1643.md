# 2026.321.1643 — chore(pins): advance the GPU base's layer-cuda pin to the driver-strip release

## Summary

`box/nvidia` — and `box/versa`, which composes the CUDA toolkit directly — pin `layer-cuda`. The release
that strips the host-coupled driver user-space is **`v2026.321.1520`** (opencharly/layer-cuda#22, merged),
so both advance:

```
box/nvidia/charly.yml:14   layer-cuda:v2026.320.2103 -> v2026.321.1520
box/versa/charly.yml:15    layer-cuda:v2026.320.2103 -> v2026.321.1520
```

**Why it matters, measured.** An image built from the previous pin baked `nvidia-utils 620.70.06`
against a host kernel module of `615.78.08` (the CachyOS repo had moved ahead of the installed driver).
The CDI injection mounts the host's *versioned* files; the image's newer copy stayed visible beside
them, and `libnvidia-ml.so.1` resolved to the baked one:

```
$ charly cmd ollama 'nvidia-smi'
Failed to initialize NVML: Driver/library version mismatch
NVML library version: 620.70          (exit 18)
```

on a perfectly healthy GPU — filed as opencharly/layer-cuda#21, fixed in the layer.

## How tested

**1. The image built from this bump carries NO driver user-space**, proven from the image itself (no
CDI injection in a plain `podman run`, so every match would be image content):

```
$ podman run --rm --entrypoint /bin/sh localhost/ollama-overlay:5fcc23c25c2f \
    -c 'echo "baked-libs=$(ls /usr/lib/libnvidia-*.so* 2>/dev/null | wc -l) baked-bins=$(ls /usr/bin/nvidia* 2>/dev/null | wc -l)"; ls /usr/lib/ollama/*/libggml-cuda.so'
baked-libs=0 baked-bins=0
/usr/lib/ollama/cuda_v13/libggml-cuda.so
```

The CUDA backend stays (it is image-owned); the driver does not.

**2. The deployed pod now resolves the INJECTED host driver**, at the running kernel module's version:

```
$ charly cmd ollama 'nvidia-smi --query-gpu=driver_version --format=csv,noheader; readlink -f /usr/lib/libnvidia-ml.so.1'
615.78.08
/usr/lib/libnvidia-ml.so.615.78.08
$ head -1 /proc/driver/nvidia/version
NVRM version: NVIDIA UNIX Open Kernel Module for x86_64  615.78.08  Release Build
```

userspace == module, from the injection only — the defect this pin bump removes.

**3. The images still build and the boxes resolve** — `charly box build nvidia` and
`charly box build ollama` both completed (`BUILD=0`), and the deployed pod was recreated from the
rebuilt chain (container `charly-ollama`, image `localhost/ollama-overlay:5fcc23c25c2f`, port 40517).

**4. The pod now offloads to the GPU — the whole model, in VRAM.** With the driver fixed and VRAM
actually available, llama.cpp places every layer:

```
$ charly ollama --server http://127.0.0.1:40517 run tiny-gpu 'Reply with exactly: GPU-OK'
GPU-OK
$ charly ollama --server http://127.0.0.1:40517 ps
NAME             SIZE       VRAM       UNTIL
tiny-gpu:latest  281.9 MiB  281.9 MiB  4 minutes from now

$ charly logs ollama | grep 'offloaded'
load_tensors: offloaded 31/31 layers to GPU
```

VRAM equal to the model size is the signature of a fully GPU-resident model, and `31/31 layers` is the
loader's own statement that nothing stayed on the CPU.

**5. What the earlier `0/29` runs were, stated plainly, because it was NOT this defect.** The same pod
earlier reported `offloaded 0/29` with the driver already correct — because the GPU was 92 % occupied
by the operator's long-running services (ComfyUI 10.9 GiB, a TTS server 3.4 GiB, a second ComfyUI
0.37 GiB), leaving ~700 MiB, and llama.cpp's fit logic refuses to place layers with that little:

```
common_params_fit_impl:   - CUDA0 (NVIDIA GeForce RTX 4080 SUPER):  0 layers, 15 MiB used, 684 MiB free
```

Freeing ~1.6 GiB (the pod's own idle models plus `charly stop comfyui-lab`, restarted immediately after
the measurement) was enough for every layer. So there were **two** independent causes of "ollama runs on
CPU": the driver shadowing fixed by this pin bump, and plain GPU capacity pressure — and the second one
is an operator capacity decision, not a defect in this change.
