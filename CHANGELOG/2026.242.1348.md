# 2026.242.1348 — feat(cstream): extend check-cstream-pod to 21 checks (B8 wl dispatchers + WP8 cstream verb)

## Summary

Extends `check-cstream-pod` from **7 checks to 21**, adding coverage for the Hyprland Lua
dispatchers (B8) and the `cstream:` verb path (WP8), and advances the boxes onto the candy versions
that make those checks resolvable.

**Boxes:**

```
cstream, cstream-check    layer-cstream-desktop  v2026.242.0422 -> v2026.242.1137
cstream-check             + plugin-cstream/candy/plugin-cstream:v2026.242.1148
punktfunk-host            layer-punktfunk        v2026.241.2026 -> v2026.242.0831
punktfunk-host            plugin-punktfunk       v2026.241.1930 -> v2026.242.1207
```

`plugin-cstream` serves the `cstream:` verb **out of process**, and charly reads its `primary:`
declaration off candies in scan range — so without it in the witness box the bed's `cstream: status`
step fails to parse with *"plugin verb cstream takes a MAP input"*. It is added to `cstream-check`
only: a shipped desktop image has no business carrying a check plugin.

### What the base bed already covered — and what this actually adds

An earlier revision of this body claimed the bed "went green while the stream did not work, because
service startup and a login page returning 200 prove neither a composited desktop nor a working
encoder." **That was false, and it is corrected here.** The 7 checks on `main` are:

```
[cstream-parent-service]    the Wayland parent service is running
[cstream-gateway-service]   the gateway service is running
[cstream-gateway-ready]     ready only when a render node AND a compositor socket exist
[cstream-stream-live]       the GWD pipeline carries LIVE content (frames change with the desktop)
[cstream-encoder-hardware]  hardware H.264 actually produces a stream (no silent CPU fallback)
[cstream-login-accepted]    a real PAM login through the session leader is ACCEPTED
[cstream-login-rejected]    a WRONG password is REJECTED by the same stack
```

So live-content gating, hardware-encode gating and both PAM legs **were already there**. This PR
does not add them, and `cstream-stream-live` / `cstream-encoder-hardware` are **pre-existing**, not
new — the earlier revision listed them among "new checks", which was wrong on both counts.

**The 14 checks this diff actually adds**, and what each makes fail:

| id | what it catches |
|---|---|
| `cstream-streamer-graph` | the streamer reaches PLAYING **and** the VA encoder it picked actually **opens** — registration is not capability |
| `wl-focus-fixture` | two windows mapped, so focus has somewhere to move between |
| `wl-focus-a` / `wl-focus-a-observed` | the `wl:` verb focuses A, **and the active window really changed** |
| `wl-focus-b` / `wl-focus-b-observed` | focus moves **both ways**, so A was not a coincidence |
| `wl-minimize-b` / `wl-minimize-b-observed` | the window really reached `special:minimized` — Hyprland has no minimize state, the special workspace *is* the idiom |
| `wl-close-focus-keep` / `wl-close-target` / `wl-close-observed` | the **named** window died and the **focused** one survived — the exact regression a focus-first close causes |
| `cstream-verb-status` | the `cstream:` verb dispatches through the provider registry |
| `cstream-verb-login-accept` / `cstream-verb-login-reject` | the verb accepts a correct credential and refuses a wrong one **against the same stack** |

That is 14, matching the diff exactly. Every `wl-*` action is paired with an **observation** check,
because asserting absence of error would pass against a compositor that silently did nothing — which
is precisely how the Lua dispatcher migration (B8) could regress unnoticed.

Both login legs are required for the same reason the base bed has both: in a rootless pod `pam_unix`
delegates to `unix_chkpwd`, which fails for *any* password when asked about another account, so a
reject-only test passes vacuously.

### 4. How the warning was eliminated, and why the cluster moves as a unit

The naive fix — advancing the one consumer that names the old version — was measured and makes it
**worse**:

| stage | warnings |
|---|---|
| untouched `main` | 1 |
| + these cstream boxes and bed | 2 |
| + advancing `pod-selkies-desktop` alone | **6** |
| + advancing the whole selkies cluster | **0** |

Advancing one consumer splits the graph against every other stale pin; only the cluster moving
together converges. Two leaf repos had to be repaired first, because each held an old pin **at its
newest tag** — so there was no tag to advance to until they were fixed:

- `opencharly/pod-kde-selkies#4` → `v2026.242.1334` (merged, tagged)
- `opencharly/layer-selkies-kde-desktop#3` → `v2026.242.1336` (merged, tagged)

The final three skews traced to an in-tree file, `candy/charly-marketplace/charly.yml`, whose stale
pixelflux pins dragged in an old `pod-selkies`; advancing those two closed it out at zero.

A third repo blocked the sync entirely and is also fixed: `opencharly/layer-github-actions#3` — its
newest tag carried a **C-style `//` comment in YAML**, which parses as a key and fails CUE for every
consumer. Before that fix this sync ended at `EXIT=1`; after it, `EXIT=0`. The broader pin backlog
remains tracked as **`opencharly/distro-cachyos#41`**.

### 5. Why `CHARLY_PLUGIN_ONLY=1`

`plugin_loader.go:434 warnSkippedFHSPlugins()` fires when the running binary is not at
`/usr/bin`/`/usr/local/bin` while `/usr/lib/charly/plugins` holds `.providers` manifests — those
belong to the installed charly **2026.187.2228**, 55 days and a schema epoch from what this tree
needs, so refusing them is correct behaviour rather than noise. `plugin_loader.go:454` documents
`CHARLY_PLUGIN_ONLY=1` as *"the supported way to resolve AS-IF-UNPACKAGED"*: it drops the FHS path
from the search, masking nothing, and its output is byte-identical to the normal run minus that line.
