# 2026.243.1924 — chore(deps): advance the candy closure to current

## Summary

204 pin lines across 24 manifests, bringing every `@github` ref in this project to its owning
repo's newest tag.

**This repo's gate reads 0 warnings both before and after, and that is the point rather than a
reason to skip it.** `main` was at 0 because it is uniformly **old** — every box resolved the same
stale entity versions, so nothing disagreed. Introduce any *recent* candy and the latent skew
surfaces immediately. A bed added on a feature branch hit exactly that: two
`resolved to multiple versions` warnings that **no edit in this repo could clear**, because the
stale versions were frozen inside other repos' published tags.

Those tags have now been repaired at their sources — **35 PRs across 20 repos**, leaves-first,
re-measuring this closure between waves — taking it from **12 conflicting candies to 0**. This
commit is that repair reaching the consumer. Without it the org-wide work is invisible here, and
the next PR that needs a current candy pays the same cost again.

## Why a full alignment rather than a partial one

Advancing pins piecemeal in a stale tree *multiplies* skew rather than reducing it. Measured on
this repo during the campaign:

| Configuration | Conflicts |
|---|---|
| a partial advance, mid-campaign | **26** |
| every in-tree ref newest, campaign incomplete | 12 |
| **this PR, campaign complete** | **0** |

Every dependency now has a current tag upstream, so a complete alignment lands consistent where a
partial one would not.

## The one unallowlisted build warning, disclosed and root-caused

`[image-build]` reports `warnings=1 allowlisted=57`. It is not a resolution conflict. From
`summary.yml`:

```
severity: warning   pattern: severity-prefix   first_line: 1735
text: "warning: wlrctl-N.N.N-N is up to date -- reinstalling"
```

That is a **pacman** notice, matched by the generic `severity-prefix` rule (any line starting
`warning:`) and not covered by an existing allowlist entry. `wlrctl` is declared by several
candies in this closure — `charly`, `distro-cachyos`, `layer-agent-forwarding` and others — so a
later layer requests a package an earlier layer already installed, and pacman reports the
reinstall. It appears 7 times in the build log.

It is a property of the **layer composition**, not of pin versions: no version comparison is
involved, and nothing about this diff creates or removes it. I have not suppressed it with a new
allowlist rule, because silencing a warning is not the same as fixing one and the honest state is
more useful to the next reader than a manufactured zero.

The two warning classes are distinct and worth separating: `charly box validate` reports **candy
resolution** conflicts — that is the gate this PR drives to 0 — while `image-build` counts lines
in the package manager's own output.
