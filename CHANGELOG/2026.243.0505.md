# 2026.243.0505 — feat(WP9b): check-cstream-gpu-vm — the GPU venue, and the VA measurement its encoder contract rests on

## Summary

`check-cstream-gpu-vm` — the **third cstream bed**, the GPU venue, and the measurement the plan's
encoder contract rests on.

The plan asserts *"a passed-through 4080 has no VA `EncSlice`"* and builds three later claims on it:
`encode: va` must fail loudly on this venue, `encode: auto` must land on software, and the encoder
gates classify by that. **That premise had never been measured.** This bed measures it, and now
**asserts** it, so it cannot silently stop being true.

The bed is safe on GPU-less hosts: `requires_exclusive: [nvidia-gpu]` maps to a vendor selector
(`0x10de`), charly writes this host's whole-IOMMU-group `<hostdev>` (so no host-specific PCI address
is committed), and without a matching card the bed **SKIPs** rather than fails.

Also adds `btrfs-progs` to `cachyos-vm` and `cachyos-gpu-vm` — both have a btrfs rootfs and no fsck
helper, so `mkinitcpio` warns *"No fsck helpers found"*, its warnings escalate to *"errors were
encountered during the build"* → `error: command failed to execute correctly`, and charly's
log-diagnostic gate fails the step **even though `deploy-add` itself exits 0**. `cstream-vm` already
carries this fix on main; these are the two remaining siblings.

## The measurement, and a defect in my own first version of it

The first version of `cstream-gpu-va-encslice` **recorded** the inventory and passed either way, on
the reasoning that asserting "no EncSlice" would make a driver that *does* offer it look like a
cstream regression. That was wrong twice over, and the bed's own green run is what exposed it:

1. **charly retains only the PASS line for a passing check.** `check-live.log` holds
   `PASS … [cstream-gpu-va-encslice] exit=0` and nothing else — stdout is not kept, and stderr is
   surfaced only on failure. So the inventory it "recorded" was **unreadable**, and the bed could
   not answer the one question it exists to ask.
2. **`vainfo` was never installed**, so the branch that always ran was the one that concludes
   nothing. Root cause: `layer-nvidia` installs the VA driver on its **fedora** arm only; the
   arch/cachyos arm installs `nvidia-utils`, which carries no VA driver and no `vainfo`. And the
   success marker `VA-INVENTORY-RECORDED` printed in **every** branch, including that one — a step
   reporting success having done nothing.

Both are fixed here. A new bed fixture `cstream-gpu-va-tooling` installs `libva-utils`, with its own
check asserting `vainfo` is present (so missing tooling fails loudly instead of silently choosing
the undetermined branch), and the check now **asserts**. When the assertion fails it prints the full
per-node inventory to stderr and says plainly that this is a **changed premise, not a regression** —
which is what the "either answer is a pass" design was really trying to protect, achieved without
giving up the gate.

*Deliberately not `libva-nvidia-driver`:* it is decode-only (VA-API over NVDEC, no EncSlice
entrypoint at all), so it would not create an encode path — only change which of two no-encode
answers the guest gives. The production cstream image does not install it either, so measuring
without it measures the real venue.

**The answer: no render node offers VA H.264 `EncSlice`. The plan's premise holds, and is now
gated.**
