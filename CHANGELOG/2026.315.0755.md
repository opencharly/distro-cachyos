# 2026.315.0755 — feat(krun-host): the libkrun runtime host box, with the check that catches an inert crun

## Summary

The W4 **`krun-host`** box the krun work needs. It composes the two layers whose absence I measured:

```yaml
base: cachyos
candy:
  - '@github.com/opencharly/layer-containerd/candy/layer-containerd:v2026.314.0705'
  - '@github.com/opencharly/layer-krun:v2026.314.0707'
```

**Why both, and why the crun build is not interchangeable.** A distro crun advertises `+LIBKRUN` while carrying **none** of the annotation vocabulary the containerd handler reads. Measured on one host, same version:

| | feature string | `strings \| grep -ci krun` | boots a guest |
|---|---|---|---|
| distro `crun 1.30.1-1` | `… +CRIU +LIBKRUN +JSON_C` | **1** | **no** |
| build of `ca04fdb6` with `--with-libkrun` | **identical** | **110** (`krun.ram_mib`, `krun.use_passt`, …) | **yes** — `uname -r` → `6.12.109` vs a `7.2.3` host |

So the box ships a check that asserts **the annotation key**, the only signal that discriminates an inert crun from a usable one.

The 11 skips are the layers' mutating `run:` steps — `verify-only mode (mutating step)`, i.e. they executed at build time and `check box` does not re-run them. No **check** skipped.

**Two checks were removed before landing, and the file says why.** The first `check box` failed on `containerd-krun-handler` (`nerdctl: command not found`) and `krun-kvm` (`/dev/kvm` absent in the check container). Both were **my** design errors, not layer defects:

- `layer-containerd` **already** asserts the handler with its own `context: [runtime]` check (`containerd-krun-absent-before-config` plus its presence sibling); a build-scope copy is the **R2 duplication** this box exists to avoid, and it cannot see a running daemon anyway;
- `/dev/kvm` is a property of the **venue**, not of the image, so it belongs to the R10 bed on the disposable guest.

**A trap this cost me a cycle to learn, recorded in the commit message too:** `check box` evaluates the plan **baked into the image**, so a plan-only edit is invisible until the image is rebuilt — the second `check box` re-reported the deleted checks with byte-identical step counts until `--tag 2026.315.probe2` was rebuilt.

**Tier `analysed on a live system`, not higher:** the box's build-scope gate is green on a built image, and the guest boot was proven by hand on this host last session (container `uname -r` → `6.12.109`), but this box has **no R10 bed yet** — that is `opencharly/layer-krun#6`, and until it lands nothing here is a live deployment proof.
